## Context

P1 asks for a browser Player that loads a versioned document and supports play,
pause, and `seek(timeUs)`, with the same frame for a golden timestamp whatever
was shown before, and with nothing loaded except the runtime build and the
declared assets. P2 asks that the Producer (PR-06) execute the byte-identical
runtime build. D12 forbids a Player↔Producer edge: code that decides pixels must
therefore live below both, in `@kadrion/renderer-dom` or the runtime build, and
the review of the plan named three such things — the page around the runtime,
the order of a frame, and when a frame counts as ready.

Evidence gathered on 2026-09-22 in the Chromium 152 of the development
machine's desktop app (informative only, not the pinned environment, Q3): in an
`iframe` with `sandbox="allow-scripts"` whose `srcdoc` carries the policy of
25.2, `origin` is `null`, `localStorage` and `parent.document` throw
`SecurityError`, `fetch` is refused, a `data:` image loads, a nested sandboxed
`srcdoc` frame (a Custom HTML element) loads and runs its inline script although
`default-src 'none'` has no `frame-src`, and its answer arrives with the frame's
`WindowProxy` as `source` and the origin `null`. Inline script text that
contains `</script` ends the script early — the probe itself broke that way.

The playground in the same Chromium (PR-05, informative): the Player loaded the
reference composition, reported `ready` at the golden timestamps, played on the
frame grid, and stopped at 9 966 666 µs; a broken image failed with
`asset-decode-failed`. Two findings: while the desktop app's browser pane was
hidden and produced no frames, `requestAnimationFrame` never fired and
`img.decode()` never settled in the sandboxed page, so the frame never became
ready; and twice a screenshot showed the status `ready` for the new time while
the Custom HTML element still showed the previous time, one frame later the
new one — the element's frame presents after the page's.

jsdom 29.1.1, where the package tests run, loads no `srcdoc`, sets no
`event.source` in `postMessage`, and has neither `HTMLImageElement.decode` nor
`document.fonts`.

## Decision

**25.1 Package.** `@kadrion/player` is the browser host (D20): it creates the
render page, speaks the protocol of 25.4 with it, owns the preview clock, and
decides no pixel. It depends on `@kadrion/schema` (validation, frame grid) and
`@kadrion/renderer-dom` (the page document of 25.2, types); it never depends on
`@kadrion/producer`, and no package depends on an application.

**25.2 The render page belongs to the renderer.** `@kadrion/renderer-dom`
exports `renderPageDocument(scripts)`, the complete document that both hosts
load:

- a `meta` Content Security Policy (below): no network at all, images only as
  `data:` URLs built from declared asset bytes, inline script and style for the runtime and for Custom
  HTML, whose `srcdoc` inherits the page's policy (D23.6). There is no
  `font-src` (no font face is registered, Q5) and no `media-src` (no playback);
- `html, body { margin: 0; padding: 0; overflow: hidden }` and one element
  `<div id="kadrion-root">`, the root of D22;
- the given scripts, each inline and unchanged. A script that contains
  `</script`, `<script`, or `<!--` (in any case) is refused with the
  `RenderError` code `unsafe-script`, because it would leave or reinterpret the
  script element.

Amended by: PR-21 (D42). The page's style also states its background:
`html { background-color: #ffffff }`. Before, the page stated none, and a pixel
that no node covers showed what lay behind its frame. The intent is that such a
pixel is opaque white in both hosts. The pixels were measured in both in the
pinned bootstrap of 2026-10-03, by the checks of D42.6, and are opaque white
there. For the Producer, white is what the code was read to produce already;
for the Player it is a change of behaviour, and the Player's check, over a host
page in magenta, is the one that tells the declaration from Chromium's default
white canvas (D42.5).

```text
default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; base-uri 'none'; form-action 'none'
```

The Player loads it as the `srcdoc` of an `iframe` whose only sandbox token is
`allow-scripts` (set before `srcdoc`, both while detached, as in D23.1), sized to
the composition's width and height in CSS pixels, never scaled: frames are
compared at the same pixel dimensions (§6.2). Fitting the preview on a screen is
the application's business and outside what parity measures. The device pixel
ratio is the browser's; PR-06 pins it for the Producer.

**25.3 A frame, and when it is ready.** The runtime build gains
`KadrionRuntime.frame(root, document, timeUs, host)`: validate (D19), evaluate,
`renderState`, and then, together, `synchronizeCustomHtml` (D23) and
`awaitMediaReady(root)`: every `img` under the root has finished `decode()`, and
`document.fonts.ready` has settled. It resolves with `{ ok: true }` only when
all of that has succeeded; a failed decode rejects with `asset-decode-failed`,
and a document without `decode` or `fonts` with `readiness-unsupported`. The
order — render, then synchronize and media, then ready — lives in the artifact,
so the Player and the Producer cannot differ in it. Font loading itself is
still open question Q5: until a font face is registered, `fonts.ready` says
nothing about the declared font, and no text pixel counts as golden (D22.6).

**25.4 Player ↔ page protocol, version 1.** The page also runs a page agent: a
script of `@kadrion/player`, serialised from one self-contained function, that
only transports messages and calls `KadrionRuntime.mount` and
`KadrionRuntime.frame`. (Since D27 it calls `KadrionRuntime.load` instead of
`mount`; amended by PR-16 (D36), 25.10, it passes the host's Custom HTML policy
to it.) It holds no pixel-relevant logic; it keeps the
document's JSON text and the bounded wait of D23. Every message is an object
with exactly the listed own keys; anything else is ignored.

| Direction     | `type`                  | Other keys                                                                                                                                |
| ------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| page → Player | `kadrion-player:ready`  | `version`                                                                                                                                 |
| Player → page | `kadrion-player:load`   | `version`, `requestId`, `document` (JSON text), `assets` (`{ id, mediaType, bytes }[]`), `ackTimeoutMs`, `customHtml` (`{ mode }`, 25.10) |
| Player → page | `kadrion-player:seek`   | `version`, `requestId`, `timeUs`                                                                                                          |
| page → Player | `kadrion-player:result` | `version`, `requestId`, `ok`, `error` (`null`, or `{ code, message, details }`)                                                           |

- The page accepts only messages whose `source` is `window.parent`; the Player
  accepts only messages whose `source` is its frame's `contentWindow` and whose
  `requestId` is the one it waits for. The origin is `null` and is not used. The
  page thereby trusts every script of the parent window: the application that
  embeds the Player is inside that trust boundary.
- The Player serialises the document once to JSON text, validates that text as
  parsed (so a getter or `toJSON` cannot make the page render another document
  than the one whose frame grid the Player uses), and sends the text; the page
  parses it in its own realm on every request, so the validator of D21 sees a
  plain object of that realm.
- **Assets and D14.** `load(document, resolveAsset)` takes the host-provided
  resolver that D14 left to the first pull request that loads assets: for every
  asset of the document, in order, it is called once with a frozen
  `{ id, type, contentHash }` and returns `{ bytes, mediaType }` or `null`. The
  Player copies the bytes, verifies their SHA-256 against `contentHash`, and only
  then sends them; `null` or a failing resolver is `asset-missing`, a mismatch is
  `asset-hash-mismatch`, a missing media type (`^[a-z]+/[a-z0-9.+-]+$`) is
  `asset-invalid` — all before the first frame, and before anything reaches the
  page. Only declared assets are asked for, so nothing else can be sent. The
  page turns the bytes into `data:` URLs. The placeholder hashes of the fixture
  (D14) never verify; a host that has bytes pins them, as the playground and the
  tests do with the bytes they generate.
- A seek's `requestId` is also the Custom HTML request ID of D23.3. The page's
  `startTimer` is its own `setTimeout` with the `ackTimeoutMs` of the load: the
  clock of the page belongs to the host (D20.2); the artifact never reads it.
- The page handles requests one after another; the Player sends the next only
  after the result of the previous one. A load waits for a seek that is in
  flight and supersedes one that waits; a result that arrives after its request
  timed out is ignored.

**25.5 Runtime identity.** `createPlayer` takes the artifact's bytes and the
expected `contentHash`, computes SHA-256 with Web Crypto, and refuses a mismatch
(`runtime-hash-mismatch`), bytes that are not UTF-8 (`runtime-unsafe`), and text
that 25.2 refuses. Because the caller supplies both, this proves integrity, not
identity: the application must take the hash from the manifest that
`@kadrion/renderer-dom` exports (`./runtime-build/kadrion-runtime.json`), and
`getState().runtimeHash` exposes the verified hash so that a parity report
(PR-10) can put it next to the Producer's render manifest (§8).

**25.6 Seek, play, pause.** `seek(timeUs)` accepts an integer in
`[0, durationUs)`, else it rejects with `time-out-of-range` before anything is
sent. One seek is in flight at a time; a seek requested meanwhile waits, and a
newer one supersedes it (its promise rejects with `superseded` before the newer
one settles). A seek's frame is fully derived from `(document, timeUs)`:
`frame` rewrites every transform and opacity and pushes the time to every
Custom HTML element, so nothing that was shown before survives. `play()` runs
the preview clock of the Player: `requestAnimationFrame` and `performance.now`
of the container's window, or a scheduler the application injects. Each tick
maps elapsed time onto the frame grid of D13 (`timeUsToFrame`, then
`frameToTimeUs`), skips the tick while a seek is in flight, and stops at the
last frame. `pause()` stops the clock.

**25.7 State and errors.** `getState()` returns
`{ status, timeUs, runtimeHash, error }` with the status `empty`, `loading`,
`seeking`, `ready`, `playing`, or `error`. `ready` means: the latest requested
time has been rendered, synchronized, and its media are ready, and nothing
newer is pending. It does not mean "presented": the browser paints afterwards,
and a Custom HTML element was seen one compositor frame late (Context). A failure leaves the status `error`, never `ready`,
even though the page may show part of a newer frame: preview may be stale, but
it is never reported as ready. `PlayerError` carries a `code`:
`runtime-hash-mismatch`, `runtime-unsafe`, `page-timeout`, `invalid-document`,
`asset-missing`, `asset-hash-mismatch`, `asset-invalid`, `asset-url-missing`,
`asset-url-unknown`, `asset-url-invalid` (from the page, which the resolver
leaves no way to reach), `asset-decode-failed`, `readiness-unsupported`,
`custom-html-timeout`, `invalid-options` (25.10),
`time-out-of-range`, `not-loaded`, `superseded`, `destroyed`, and `page-error`
for anything else the page reports. Load errors arrive before the first frame.

**25.8 Guardrails.** The sources of `@kadrion/player` may not use the network:
`fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `Worker`, `SharedWorker`,
`importScripts`, `sendBeacon`, and dynamic `import()` are rejected by ESLint.
The list is a best effort, not a proof: it does not see a `src` attribute set on
an element, `window.open`, `RTCPeerConnection`, `WebTransport`, or a computed
name such as `globalThis['fetch']`; review covers those. The page agent must stay
serialisable with `String(fn)`: a bundler option that rewrites functions
(`keepNames`) or coverage instrumentation would change its text, and the tests
of the page would then fail. No package source imports an application, and `apps/playground` depends only on
`@kadrion/player`, `@kadrion/renderer-dom` (the artifact and its manifest), and
`@kadrion/test-fixtures`.

**25.9 Playground.** `apps/playground` is a workspace member, not a package: a
page with play, pause, and the five golden seeks over the reference composition,
placeholder asset bytes generated in the browser (no binary enters Git), and a
local static server that serves only the built files it names. It holds no
domain rule.

**25.10 Amendment of PR-16 (D36): the host's Custom HTML policy.** Recorded at
the project owner's request on 2026-09-27, implementing D36.

- `createPlayer(container, options)` takes `options.customHtml`:
  `{ mode: 'disabled' }` or `{ mode: 'trusted' }`. Absent means `disabled`;
  only an explicit `trusted` runs Custom HTML. Anything else rejects with the
  `PlayerError` code `invalid-options` before the render page is created. The
  policy is the host's and holds for the Player's lifetime; it is never read
  from a document.
- Every `kadrion-player:load` carries it as `customHtml: { mode }`. The page
  agent accepts only exactly that shape with a known mode (anything else is
  ignored, like every malformed message) and passes `{ customHtml }` to
  `KadrionRuntime.load`, which requires it (D23.10). The protocol stays version
  1: the Player and its page agent are one build.
- `disabled`: the render page mounts every Custom HTML element as an empty
  placeholder of the same geometry, with no frame; no script, message, request,
  or WebRTC of an element can start (D23.10).
- `trusted`: this ADR and D23 hold unchanged. It is the host's decision to run
  the document's code, not network isolation (D36). The page's
  `Permissions-Policy` and response headers stay the host's responsibility.

## Alternatives considered

- **The page document and agent only in `@kadrion/player`** — the Producer would
  have to copy what decides its pixels, or cross the edge D12 forbids.
- **The agent inside the runtime build** — the artifact would need `parent` and
  a timer, both banned there (D20.2, D24.5); a lent port adds a protocol without
  removing the transport.
- **Blob URLs for assets** — jsdom has no `URL.createObjectURL`, and a `blob:`
  URL of another origin is not clearly loadable from an opaque origin; `data:`
  URLs are deterministic and load in the probe.
- **A policy with hash sources for the runtime** — `'unsafe-inline'` is ignored
  once a hash source is present, which would block the inline scripts of Custom
  HTML, whose `srcdoc` inherits the policy.
- **Reporting ready after the Custom HTML acknowledgement only** — an image may
  still be undecoded (the review of the plan).

## Consequences

- `@kadrion/renderer-dom` exports `renderPageDocument`, `awaitMediaReady`, the
  artifact `./runtime-build/kadrion-runtime.js`, and its manifest
  `./runtime-build/kadrion-runtime.json`; `tests/repo/workspace-structure.test.ts`
  allows these exports for this one package. The runtime build gains `frame`.
- P1 is **not** proven by PR-05: its evidence is an automated browser test, and
  jsdom enforces neither sandbox nor policy, decodes no image, and loads no
  font. PR-05 proves the Player's logic in jsdom through a harness that loads the
  page and the element documents, models the source of messages, and stands in
  for `decode` and `fonts`; PR-06 runs the P1 test in pinned Chromium (Q3, Q14).
  The manual check of the playground in the desktop app's Chromium is
  informative only.
- A preview in a document that produces no frames (hidden tab or pane) never
  becomes `ready`, because `decode()` waits for rendering; the Player reports
  `page-timeout`, never a stale ready frame.
- PR-06 must capture a frame only after one in which the Custom HTML element has
  presented its new state (for example a compositor frame after the result, or a
  capture API that waits for one); the late element of Context is otherwise a
  real parity error between preview and reference.
- Hypothesis for PR-06: the page's `default-src 'none'` may govern where the
  nested Custom HTML frame can navigate to, and so close D23.7's self-navigation
  gap in both hosts. It is measured, not assumed.
- PR-06 builds the Producer on `renderPageDocument` and `KadrionRuntime.frame`,
  with its own agent or a CDP call, and records the runtime hash in its render
  manifest.

## Verification

- `packages/renderer-dom/test/render-page.test.ts`: the exact page document,
  the refused script sequences, and readiness (`frame` waits for decode and fonts,
  and fails typed).
- `packages/player/test` (jsdom, harness): the page `srcdoc` (policy, exactly
  two scripts, the artifact byte for byte); the five golden timestamps render the
  hand-derived trees and the element's bar; the same tree after a fresh load,
  after playing, and after seeking backwards; the resolver asked once per
  declared asset, the fixture's placeholder hashes refused, and exactly the
  verified bytes sent; typed errors before the first frame for a missing asset,
  a failing resolver, a hash mismatch, an invalid document, a runtime hash
  mismatch, and unsafe runtime text, and never `ready`, with nothing sent to the
  page for the ones the Player refuses itself; a Custom HTML element that does
  not answer yields `custom-html-timeout`, never `ready`; forged messages are
  ignored in both directions; superseded seeks settle in order; a load waits
  for a seek in flight and supersedes a waiting one; a late result after a
  timeout changes nothing; play follows the frame grid with an injected
  scheduler and stops at the last frame.
- `tests/repo/lint-guardrails.test.ts` and `tests/repo/playground.test.ts`: the
  network ban and the application boundary.
